# アセット生成パイプライン（試行錯誤の記録）

ドパミン・モールのアセット（キャラクター・マップチップ・アイテム・小物）を、
画像生成モデルで作ってゲームに組み込むまでの手順書。
**まだ試行錯誤の途中。** うまくいったこと・いかなかったことをそのまま残し、
手順が安定したらこのドキュメントを更新する。

最終更新：2026-11-26（壁を高く・サイズ正規化・デバッグモード追加）

## 全体像

1. 仕様を決める（アセット一覧、向き、フレーム数）
2. 画像生成モデルでスプライトシートを生成する
3. シートを切り出して透過 PNG にする
4. ゲームに組み込む（向き・アニメーション）
5. プレビュー画像と実機で確認する
6. コミットして Release に載せる

## 1. 仕様を決める

- 追加するアセットを一覧にする（キャラクター名・種類・マップチップの用途）。
- キャラクターは **8方向**（南・南西・西・北西・北・北東・東・南東）で描く。
  南＝正面（手前向き）、北＝背面（奥向き）。
- 歩行フレームは **4コマ**（左足前・通過・右足前・通過）。1歩で2フレーム進む
  （1歩目：フレーム0→1、2歩目：フレーム2→3）。足の振りを大きく、交互に
  踏みしめるのがはっきりわかる絵にする。
  **注意：4コマのシートは部分的に壊れやすい。** 画像生成モデルは「通過」フレームで
  頭を下げたり、かがみ込んだり、後頭部に顔を描いたりする。必ず切り出し後の
  コンタクトシートによる品質ゲートを通すこと（後述）。
- 攻撃は専用フレームを作らず、**突進＋斬撃エフェクト**で表現する。
- マップチップの原則：**1マス＝1つのチップ**。壁は上面と前面を1つのチップに含める。
  面（上面・前面・角）を別々のスプライトに分けると、壁の位置計算が複雑になって
  描画がガチャガチャする（2026-11-26 の反省）。
- **壁はタイルより背が高い**（幅64×高さ128＝タイル2枚分）。下端をタイルの下端に
  合わせ、上に1タイル分はみ出して描く。上面（明るい色）と前面（暗い色）の境が
  ちょうど中央に来るように切り出す。描画順は行ごとのペインター法のままで、
  はみ出しが上の行の床の上に、壁より手前（南）の行のキャラクターが壁の前面の
  上に描かれる。壁が連続する場所では上面の模様がつながって見える。
  （2026-11-26、平らな64x64の壁チップではのっぺりして見えたため変更）
- **見下ろしは平らに**。チップは真上からの平らな見下ろしで描く。斜めの線が入った
  チップ（アイソメの立方体・斜めのベンチなど）は見下ろしでは違和感が出る。
  プロンプトには `top-down view with straight vertical direction like Shiren
  the Wanderer` と書き、斜めの表現を避ける。

## 2. シートを生成する（画像生成モデル）

### プロンプトの型

- 画風：`Retro pixel-art game sprite sheet` に見下ろし方式を付ける。
  現在はシレン風の縦方向が真っすぐな見下ろし（`top-down view, vertical direction
  straight up and down, not isometric`）。以前は2.5Dアイソメトリックだったが、
  視認性・操作性の理由で見下ろしに変更した（2026-11-26）。
- 配置：行と列をはっきり指定する（例：`3 rows x 8 columns`、行＝キャラクター、
  列＝向き）。向きの順番は必ず列挙する（南、南西、西、北西、北、北東、東、南東）。
- 背景：`solid bright magenta #FF00FF background`。切り出し時の透過キーにする。
- 区切り：`with wide gaps between cells`（スプライト同士を離す。くっつくと切り出せない）。
- 禁止事項：`no text, no shadows on the background`（影があると透過処理で残る）。

### Spritefy方式（安定したキャラクター生成）

参考資料（Etsu 共有、2026-11-26）：Spritefy ブログ3本。
「Creating Consistent Pixel Art Characters With AI」
「How to Make a Sprite Sheet With AI」
「How to Make an 8-Directional Character Sprite」。
要点は **大きなシートを1回で作らない** こと。従来の失敗（8方向×2〜4フレームを
1枚のシートで生成）は、モデルがセルごとにキャラクターを再解釈して壊れるのが原因だった。

1. **キャラクター仕様を短く書く**：身長・頭身・シルエット・配色・持ち物の手・
   輪郭・カメラ・光の方向を、合否判定できる形で決める。
   主人公の仕様：緑のフード（先の尖ったフード）・茶髪・ベージュのチュニック・
   茶色のブーツ、左手にブドウとパンの入った編み目のかご。セル64x64、足は下端の
   ベースラインにそろえる。光は左上から暖色。
2. **マスター参照を1枚作って承認する**：描くのは5方向（南・南東・東・北東・北）の
   静止ポーズだけ。まず4方向（南・東・北と西＝東の反転）の基本形を承認し、
   斜めはその間を補間する。**マスターが壊れていたら次に進まない。**
   主人公のマスターは1回目で南東と東がほぼ同じ絵・北東がフードなしの髪だけに
   なったため、斜めの説明を書き直して再生成した（2回目で承認）。
3. **動きは1アクションずつ、マスターを参照画像にして生成する**：
   歩行は南・南東の2行と東・北東・北の3行に分けて2回に分けた。
   1行＝1方向、1列＝1フレーム（左足前・通過・右足前・通過）。
   1回の生成で扱うセルは8〜12枚までに抑える。
4. **残りの3方向は反転で作る**：南西＝南東の左右反転、西＝東の左右反転、
   北西＝北東の左右反転。持ち物の手が入れ替わる点に注意（かごは左右が逆になる。
   気になる場合はその方向だけ別に描く）。
5. **切り出してからコンタクトシートで全セルを確認する**（品質ゲートは従来通り）。
   フレームを50%不透明で重ねて頭・肩・手・足の位置がずれないか見るとよい。
   1枚でも壊れたフレームがあれば、そのフレームだけ差し替える（全体の再生成はしない）。

主人公v2の試行結果（2026-11-26）：マスター参照（5方向）＋歩行2シートで、
8方向×4コマ＋静止の計40セルを作り、**不良セルは0** だった。
切り出しは連結成分法で成分数が期待通り（5・8・12）に出て、行ごとの高さも
そろっていた（南562px、南東545px、東450px、北東439px、北446〜447px）。
ただし2枚の歩行シートで描画スケールが少し違った（南・南東の方が東・北東・北より
大きい）。また静止フレーム（マスター）は歩行フレームより大きい（約680px対
約450〜560px）。ゲームへの組み込み時は `tools/make_norm.py` による
方向ごとの倍率正規化で吸収する。
保存先：`samples/sheets-hero-v2/`（マスター参照・歩行シート・切り出し済み
`sliced/`・コンタクトシート `hero2_contact.png`・組み込み後のコンタクトシート
`hero2_final_contact.png`）。

主人公v2の組み込み（2026-11-26）：`tools/slice_hero2.py` で切り出し済み PNG
（生の切り出しサイズ、最大で約689px）からマゼンタ背景を抜いて最大辺160pxに
縮小し、`hero_d<向き>_f<フレーム>.png`（歩行4コマ）と `hero_d<向き>_idle.png`
（静止）として `android/assets/sprites2d/` に入れた。古い主人公スプライトは
すべて置き換えた（同じファイル名で上書き）。マゼンタ抜きの注意点：
厳密な純マゼンタだけを抜くと、縮小時の LANCZOS のリンギングでピンクの
フリンジが復活する（1回目の変換で各スプライトに数十〜200px残った）。
リサイズ前にマゼンタ混色も抜く方式（`tools/slice_sheets.py` の
is_magenta_pixel と同じ条件）にし、リサイズ後にも純マゼンタ抜きをもう1回
行うことで、残量は0〜34pxまで減った。紫ブドウはこの条件では残る
（各フレームに150〜180px前後残っていることを数えて確認）。
止まっているときは静止フレーム、移動の補間中は歩行4コマを使う
（`MallScreen.drawPlayer` に `playerMoving()` で切り替える。歩行フレームの
決め方自体は従来通り）。デバッグモードの「停止」「武器使用」の行も
静止フレームを使う（`debugSpriteName` で行ごとに切り替える）。
`tools/make_norm.py` は静止フレームも測るようにした：方向の倍率は歩行
フレームの面積の中央値から決め、静止フレームにはさらに
（歩行フレームの内容の高さの中央値／静止フレームの内容の高さ）を掛ける。
組み込み後の測定結果：主人公の方向ごとの倍率は 0.969〜1.009（旧主人公は
0.93〜1.09）。面積のばらつきが最大1.44倍から約1.08倍に縮まり、Spritefy方式の
効果が数値でも確認できた。敵の倍率は再生成で変わっていないことを確認済み。
`tools/compose_hero.py`（旧主人公の合成用）は今は使っていない。

### うまくいかなかったこと

- **プログラム生成の限界**：最初は Pillow で計算生成していた（`tools/generate_tiles.py`）が、
  どうしても Y2K な雰囲気になってしまった。画像生成モデルへの切り替えが正解だった。
- **向きの取り違えの危険**：シートの列の順番をプロンプトで明示しないと、向きがずれる。
  切り出し後に必ずコンタクトシートで目視確認する（客と店員の取り違えなど）。
- **マゼンタのフリンジ**：霧やランプなど半透明に近い絵は、マゼンタ背景と混色して
  ピンクがかった縁が残る。低 alpha で描けばほぼ目立たないが、完全な解決ではない。

## 3. 切り出して透過 PNG にする

- スクリプト：`tools/slice_sheets.py`（Pillow＋scipy連結成分法）。
  マゼンタ背景を透過にし、グリッド位置で成分を割り当て、最大辺 160px に縮小する。
- 入力は WebP でも Pillow で読める。
- 出力先：`android/assets/sprites2d/`。対応表は `manifest.json` に残す。
- **切り出し後はコンタクトシートを作って目視確認する。** 向きの取り違え・欠け・
  フリンジがないかを見る。ここを省くとゲーム内で気づきにくい。
  品質ゲート用のコンタクトシートは `tools/check_sprites.py` で作る
  （`samples/sheets-flat/check_*.png`）。向き・フレームのラベル付きで大きく並べる。
- **主人公の歩行フレームは合成する**（`tools/compose_hero.py`）。
  4コマ版シートは部分的に壊れているため、品質ゲートの結果をもとに方向ごとに
  使うフレームを決める。不良セルは予備の2フレーム版シートの同じ向きのフレームで
  置き換え、列全体が使えない向きは予備シートの2フレームをそのまま使う
  （f0,f1,f0,f1 と並べて4フレーム化）。合成の対応表は
  `samples/sheets-flat/hero_composition.json` に残し、同じ内容を
  `tools/compose_hero.py` のコメントにも書く。合成後は `hero4_*`／`hero2_*` の
  作業用ファイルを削除し、`manifest.json` を実際の PNG から作り直す。
- 旧スプライトは置き換わったら削除して APK を軽くする
  （プログラム生成の `android/assets/sprites/` 34枚は 2026-11-26 に削除済み）。
- **縦長の壁は専用の切り出しスクリプトを使う**（`tools/slice_wall.py`）。
  1枚の WebP から上面と前面の境が中央に来るよう 972x1944 に切り出し、
  マゼンタ背景を透過にして `wall.png` にする。`manifest.json` の wall 項目も更新する。
- **キャラクターの実寸は `tools/make_norm.py` で測る。**
  各スプライトの内容の bounding box（不透明ピクセルの範囲）と不透明ピクセル数
  （見た目の「大きさ」の目安）を測り、`android/assets/sprites2d/norm.json` に
  書き出す。方向ごとの表示サイズ正規化の倍率もここで決める（後述の §4 を参照）。
  測定結果は実行時の出力に表示されるので、ばらつきの確認に使える。

## 4. ゲームに組み込む

- 読み込み：`Sprites.java`（`sprites2d/` から読込、Linearフィルタ）。
- 向き：プレイヤーと敵に「向き」（0〜7、南から時計回り）を持たせ、移動・攻撃した
  方向を向く。向きに合ったスプライトを描く。
- 歩行：移動の補間（約0.12秒）に合わせて主人公は4フレームを切り替える。
  歩数パリティ（`walkStep`）で1歩目はフレーム0→1、2歩目はフレーム2→3。
  止まっているときはフレーム0。上下の跳ねと組み合わせて歩いている感じを出す。
  敵は上下の跳ね＋向きの切り替えでよい。
- 攻撃：攻撃方向へ素早く突進して戻る（0.18秒、0.35マス）＋斬撃エフェクト（白い弧）
  ＋対象のフラッシュ（黄色い星）。
- 8方向シートがない種類（ウサギの着ぐるみ・サル・ツチノコ・雪男・獅子の神・
  3種のボス）は従来の1枚絵をフォールバックとして使う。
- 移動とキー：矢印キー／WASD は画面の方向（上＝画面の上、下＝画面の下、左＝画面の左、
  右＝画面の右）。残りの4方向は Q／E／Z／C。ゲームパッド・Fire TV リモコンの
  十字キーは画面の4方向。斜め移動も1ターンで移動できる。敵AI・視界のBFSも8方向。
- **注意：Q/E/Z/C の対応は一度間違えた。** 座標変換の数式で検証すること。
  見下ろしでは画面の上＝北（y が減る方向）、下＝南（y が増える方向）。
  正しい対応：Q＝北西(-1,-1)、E＝北東(1,-1)、Z＝南西(-1,1)、C＝南東(1,1)。
  指示の値を鵜呑みにせず、数式で確かめること。
  （旧アイソメ時代の対応：Q＝北西(-1,0)、E＝北東(0,-1)、Z＝南西(0,+1)、
  C＝南東(+1,0)。座標系が変わったら対応表も作り直すこと。）
- 向きの対応表（見下ろし）：0=南(0,1)、1=南西(-1,1)、2=西(-1,0)、3=北西(-1,-1)、
  4=北(0,-1)、5=北東(1,-1)、6=東(1,0)、7=南東(1,1)。向きとスプライトの列の
  順番（南、南西、西、北西、北、北東、東、南東）は同じ。
- 描画：タイルは `tileX(x)=x*64`、`tileY(y)=-y*64` で並べる（libGDX のワールド
  座標は Y が上向き）。描画順はペインター法で行ごとに上から下へ。
  壁チップは幅64×高さ128（タイル2枚分）で、下端をタイルの下端に合わせて描く。
  面分割の描画コードは削除済み。
- **キャラクターの表示サイズ正規化**（`Sprites.java` が `norm.json` を読む）。
  測ってわかったこと：スプライトは切り出し時に最大辺160pxにそろえてあるため、
  内容の高さはほぼ全方向で 156〜160px とそろっている。向きによる「大きさ」の
  ばらつきは高さではなくシルエットの面積（横幅・かさ）に現れる。例えば主人公の
  停止フレームは方向で 8771〜12629px、犬は 9127〜15768px と最大1.7倍の差がある。
  そこで方向ごとに倍率を決める：その方向のフレームの面積の中央値を、その
  キャラクター種別の基準面積（8方向の中央値）で割った平方根。同じ方向の
  全フレームに同じ倍率を使うため、歩行中に大きさが脈打つことはない。
  1枚絵しかない種類は方向によるばらつきがないため倍率 1.0。
  描くときは内容の下端（足元）がタイル位置に、内容の横中心がキャラクターの
  中心に来るよう補正する。姿勢そのもののばらつきは絵の問題なのでコードでは
  直せない。大きさのばらつきだけを抑える。
- **キャラクターの足元の影**：`Sprites.java` で Pixmap から楕円のグラデーション
  テクスチャを作り、キャラクターの地面の位置に描く。のっぺり感を軽くする
  ための小さい工夫。Bloom・Depth of Field・ライティングのシェーダーは未実装。
- **スプライト確認デバッグモード**（アプリ内、タイトル画面から開く）。
  タイトル画面のメニュー「スプライト確認」または F1 キーで開く。左右キー
  （A／D キーでも可）でキャラクター種別（主人公＋敵14種）を切り替える。
  8方向を列に並べ、行を「停止」「歩行」「武器使用」の3段にした一覧を表示する。
  歩行は実際の歩行フレームをアニメーションさせ、武器使用はゲーム内の攻撃
  アニメーション（突進＋斬撃＋フラッシュ）をその向きで再生する。
  各セルの下に実寸（幅×高さ）とフレーム数を出し、方向ごとの表示倍率も一覧の
  上に表示する。1枚絵しかない敵はその1枚を表示し、フレーム数1と出す。
  Bボタン／Backキー／Escキー／F1キーでタイトル画面に戻る。
  キーボード（矢印キー＋Enter）とゲームパッド・Fire TV リモコン（十字キー＋A）の
  両方で操作できる。タイトル画面のタップ操作：スプライト確認のメニュー行を
  タップするとデバッグモード、それ以外はゲーム開始。
  デバッグモードの画面のプレビューは `tools/preview_iso.py` が
  `samples/preview25d/debug_sprites.png` に作る（ローカルのみ）。
  タイトル画面のキー案内と README の操作説明に開き方を書くこと。
  日本語フォントのサブセットは `tools/subset_font.py` で作り直すこと
  （新しい日本語文字列を足したら必ず再生成する。フルフォントは
  `/tmp/NotoSansJP-Regular.ttf` に置く。入手方法は同スクリプトの冒頭を参照）。

## 5. プレビューと確認

- プレビュー生成：`tools/preview_iso.py`（ゲーム本体と同じ座標計算で 1280x720 を描く）。
  下層（明るいモール）と上層（霧とランタンの神秘）の2枚を作る。
  デバッグモードの画面のプレビュー（主人公）も同じスクリプトが
  `samples/preview25d/debug_sprites.png` に作る。
  プレビュー画像は `samples/preview25d/`（ローカルのみ、コミットしない）。
  プレビューでは壁の高さと重なり・足元の影・主人公の4フレームの違いを目視確認する。
- **実際の起動・プレイ確認は VM ではできない**（ディスプレイなし、Gradle もローカルでは
  動かない）。CI ビルド成功までが VM での確認範囲。実機（Fire TV／PC）での確認が必須。
  実機確認項目：視認性、斜め移動の操作感、ゲームパッドのボタン挙動、攻撃アニメの見た目、
  霧・オーバーレイの暗さ、壁の見え方。
- 足の踏みしめ問題（2026-11-26）：遊んだビルドは上下の跳ねだけで、足が交互に出て
  いなかった。歩行フレームは足の振りを大きくし、切り替えが実際に目に見えるか
  プレビューと実機の両方で確認する。

## 6. コミットとリリース

- `git add -A` は使わない。必要なファイルだけ個別に add する。
  （一度 `samples/` を誤ってコミットしたことがある。`samples/` は `.gitignore` 済み）
- コミットして main へ push すると GitHub Actions が自動でビルドする。
  別途 `gh workflow run` は不要（重複実行を避ける）。
- 手元の VM では Gradle が動かない（サンドボックスが TCP をブロックするため）。
  検証は CI の実行でのみ行う。失敗したらログを読んで修正し、最大3回まで再実行する。
- 成功したら `gh release view nightly` で APK と `dopamine-mall-desktop.jar` の
  両方が更新されたことを確認する。
- 日次ビルド：毎日 09:00 JST に GitHub Actions が走り、nightly Release を更新する。
  Release ページ：https://github.com/nutomu/dopamine-mall/releases/tag/nightly

## 音楽（アセット生成の補足）

- **音楽生成モデルは手元にない。** 使えるのは Spotify 再生・ナレーション生成・TTS のみ。
  BGM はシンセサイズのチップチューンで作る（`tools/generate_music.py`、Python 標準ライブラリ
  の `wave`＋`math` で方形波・三角波・正弦波を合成）。
- 作曲の充実ポイント：メロディにハーモニー（3度下）、ウォーキングベース、
  カウンターメロディ、進行の変化（ダンジョン後半 Am–F–Dm–E、ボス後半 Fマイナー寄り）、
  低いドン（サイン波）。
- OGG 変換：ffmpeg で WAV→OGG（libvorbis q4）。音楽データ 2.35MB→約310KB。
  WAV はリポジトリから削除する。

  ばらつきは面積に出る（主人公の停止フレームで最大1.44倍、犬で最大1.73倍）。
  壁の上面と前面の境が中央に来るよう切り出しを調整した（972x1944）。
  ライティング・シェーダー（Bloom・Depth of Field・ボリュームライト）は
  参考資料（Qiita「2Dゲームのリッチなビジュアルを実現する技術調査」）の方向性として
  控えてあるが、今回は実装しない方針。
- 2026-11-26：Spritefy方式で主人公を作り直す試行。マスター参照（5方向の静止）
  を作って承認し、歩行は1アクションずつマスターを参照画像にして生成、
  残り3方向は左右反転で作った。8方向×4コマ＋静止の40セルで不良セル0。
  従来の大きなシート1枚での生成（8方向×2〜4フレーム）より安定した。
  歩行シート2枚で描画スケールが少し違ったが、正規化で吸収できる。
  詳しくは §2 の「Spritefy方式」を参照。

  最大辺160pxに縮小して `hero_d<向き>_f<フレーム>.png` と `hero_d<向き>_idle.png`
  に置き換え、止まっているときは静止フレームを使うようにした。方向ごとの倍率は
  0.969〜1.009 と旧主人公（0.93〜1.09）より大幅にそろった。敵の倍率は変わらず。
  マゼンタ抜きはリサイズ前後に2回行うこと（LANCZOS のリンギングでフリンジが
  復活するため）。
- 2026-11-27：主人公は現代のドパガキだと訂正された（中世フードの主人公v2は
  ヌトムの試作の選択で、にゅーいちの仕様ではなかった）。SpriteKiln の
  スプラッシュアート方式で作り直し（v2、IoU 0.750、38色）。姿勢・シルエットは
  良いが「ピクセルアートというより昔のポリゴンみたい」との指摘で、画風の異なる
  スプラッシュ4枚（フラット／ちび／レトロピクセル／コミック）で実験。

  陰影＋細い輪郭）」。にゅーいちがレトロピクセルアート調（hero-004、IoU 0.785、
  21色）を選び採用。スプラッシュ＋スプライトの組みで持つグラフィックス管理
  （`graphics/`＋`registry.json`＋通し番号）を導入。詳しくは
  `docs/CHARACTER_GRAPHICS.md` を参照。

## 7. キャラクターグラフィックス管理（2026-11-27〜）

- キャラクター・モンスターは、スプラッシュアート（1枚絵）と歩行スプライト
  （8方向×歩行4コマ＋静止）の組みで持つ。ダンジョン内はスプライト、
  図鑑・ステータス表示はスプラッシュアートを使う。

- 採用中の主人公は hero-004（レトロピクセルアート調）。
