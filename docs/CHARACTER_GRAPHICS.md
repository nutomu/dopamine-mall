# キャラクターグラフィックス管理

キャラクターとモンスターのグラフィックス（見た目）を、スプラッシュアートと
歩行スプライトの組みで管理する仕組み。2026-11-27 に、にゅーいちの提案で導入し、
同日ににゅーいちの修正で「画風はゲーム全体のもの」「番号はデザインの
バリエーション」という扱いに直した。

## 考え方

- キャラクター・モンスターは1体ごとに、**スプラッシュアート（1枚絵）と
  歩行スプライト（8方向×歩行4コマ＋静止）の組み**で持つ。
- 用途で使い分ける：
  - **ダンジョン内（ゲームプレイ中）はスプライト**を使う。
  - **図鑑やステータス表示ではスプラッシュアート**を使う。
    （図鑑・ステータス画面自体はまだない。スプラッシュの同梱だけ先に行う）
- パターンは何種類でも作れる。**どれを採用するかは後から選べる**。
  採用中のものだけがゲームに入る。候補はリポジトリに残し、見比べられるようにする。

## 画風はゲーム全体のもの（キャラごとの採用ではない）

- **画風はゲーム全体のアートに適用して統一感を持たせるもの**。
  キャラクターごとに画風を選ぶのではない。
- 現在の画風：**レトロピクセルアート調（バージョン1、2026-11-27 決定）**。
  4バリアント実験はゲーム全体の画風選びであって、ピクセル版がゲーム全体の
  画風として採用された。
- **画風はあとで調整することもある。その場合は最悪グラフィックスは全部
  再生成になる。** 各パターン／アセットに画風のバージョンを記録して、
  再生成のときに追跡できるようにする（`registry.json` の `style` と、
  各 `meta.json` の `style`／`style_version`）。
- 画風を変えるときは、新しい画風のバージョンを決め、その画風で
  全グラフィックスを作り直す。バージョン番号を上げ、変更前のアセットは
  旧バージョンとして記録に残す。

## 通し番号とバリエーションのルール

- キャラクターごとに3桁の通し番号を振る。主人公は `hero-001`〜、
  モンスターは `monster-001`〜（モンスターは今後追加する）。
- **番号は「まったく違うデザイン」のバリエーションに付ける**。
  服装が全く違う・髪型が全く違う・配色が全く異なる、まったく外観的特徴が
  異なるバリエーションであること。同じキャラの画風違いだけでは、生成される
  スプライトにあまり変化が出ないため、バリエーションにはならない。
  ただしテイストはゲームの世界観で統一する。
- 番号はプロンプトで指定しやすくするためのもの。
  新しいパターンを作るときは「hero-001のデザインで」と指定できる。
- 番号は一度振ったら変えない。採用が変わっても番号はそのまま。

## 保管場所：実体はGitHub、ダッシュボードはメタデータ＋URLのみ

- グラフィックスの実体（画像・アトラス）は **GitHub の `graphics/` ツリー**に置く。
  ダッシュボードのアーティファクトにバイナリを置くとストレージを食うため、
  ダッシュボードにはメタデータ（名前・画風・IoU・色数・状態）と
  GitHub raw URL だけを登録する。
- 台帳は `graphics/registry.json`。`current` が採用中のパターンを指す。
  台帳に載せるのは hero デザイン（今は hero-001 のみ）。画風実験は台帳には
  載せず、この設計書から参照させる。

## ディレクトリ構成

```
graphics/
  registry.json                  # 台帳（画風＋heroデザイン一覧＋採用中の指定）
  hero/
    001/                         # hero-001（パターン番号＝ディレクトリ名）
      splash.webp                # スプラッシュアート原画
      atlas.png                  # 歩行＋待機のアトラス（1024x2048、128pxセル）
      atlas.json                 # アトラスのフレーム情報（frameTags）
      meta.json                  # 画風・画風バージョン・IoU・色数・QA・元ディレクトリ・日付・備考
      contact.png                # コンタクトシート（8方向×待機＋歩行）
  style-experiments/             # 画風選びの実験（heroのバリエーションではない）
    v2/ flat/ chibi/ comic/      # 同じ構成（splash.webp・atlas.png・atlas.json・meta.json・contact.png）

android/assets/
  splash/hero.png                # 採用中のスプラッシュを同梱したもの
                                 # （libGDX は webp を読めないため PNG に変換。
                                 #  高さ1024px程度に縮小してサイズを抑える）
  sprites2d/hero_d0_f0.png ...  # 採用中のスプライト（8方向×歩行4コマ＋静止）
  sprites2d/norm.json            # 方向ごとの表示サイズ正規化の倍率
```

`registry.json` が持つもの：`style`（ゲーム全体の画風名・バージョン・決定日・
注意書き）、`current`（採用中のパターン）、`characters`（各キャラの
エントリ一覧）。各エントリが持つもの：`id`、`character`、`style`、
`style_version`、スプラッシュ・アトラス・コンタクトシート・meta のパス、
`iou`、`colors`、`status`（`採用`／`候補`）、`notes`（備考）。

### 画風選びの実験の記録（2026-11-27、heroのバリエーションではない）

4枚のスプラッシュアート（同じドパガキ、画風違い）で SpriteKiln を試し、
ゲーム全体の画風を選んだ記録。`graphics/style-experiments/` に残してある。

| 実験 | 画風 | IoU | 色数 | 結果 |
| --- | --- | --- | --- | --- |
| v2 | スプラッシュアート方式 v2（v3マスター） | 0.750 | 38 | 姿勢・シルエットは良好だが「昔のポリゴンみたい」との指摘で実験へ |
| flat | フラットアニメ調 | 0.776 | 39 | v2とほぼ同じ見た目。スプラッシュの平たさは引き継がれず |
| chibi | ちび・デフォルメ調 | 0.677 | 38 | 最もゲームキャラらしいSD体型だが、陰影は柔らかいまま |
| comic | コミック調 | 0.730 | 39 | 最も太く大胆で鮮やか。原画の足元に黒い地面影の筋あり |
| **pixel** | **レトロピクセルアート調** | **0.785** | **21** | **採用（hero-001）。色が一番フラットで硬い** |

結論：スプラッシュアートの画風を変えても、**変わるのはパレットと
プロポーションだけ**。フラットなスプラッシュを使っても出力はv2とほぼ同じに
なった。「昔のポリゴンみたい」という印象の原因は**レンダラー側**にある。
SpriteKiln の滑らかな SDF シェーディングと細いセレクティブ・アウトラインが
そのままで、スプラッシュの平たさや角ばったドットは引き継がれない。
ピクセルアートらしくするレバーはレンダラー側にある：
陰影を soft→flat にする、ランプの段数を減らす、ディザ、PerfectPixel 式の
共有パレット量子化＋グリッドスナップ。
4バリアントは全て歩行ゲートを通過した（不良セル0、ソール円盤なし、
スマホ左手・缶右手が正しい手にある）。

## パターンの追加手順（新しい hero バリエーション）

1. **まったく違うデザイン**で作る。服装・髪型・配色のいずれもが hero-001 と
   明確に違う外観にすること。同じキャラの画風違いはバリエーションにならない。
   テイストはゲームの世界観で統一する。画風は現在のゲーム全体の画風
   （レトロピクセルアート調 v1）で描く。
2. スプラッシュアートを作る（1枚絵、正面全身、マゼンタ背景）。
3. SpriteKiln のスプラッシュアート方式でモデル化する
   （`spritekiln ref prep` でパレット抽出、仕様を書く、モデル化、
   `ref compare` で IoU ≥ 0.65 を目指す、アートディレクションで修正、
   歩行＋待機をレンダリング）。詳しくは `docs/ASSET_PIPELINE.md` を参照。
4. 歩行ゲートを通す（足シートを先に、フレーム単位で目視確認）。
   f0/f2 で逆の足、f1/f3 は足を閉じたパッシング、ソール円盤なし、
   斜めは体も三-quarter、持ち物が正しい手にあること。
5. 次の番号のディレクトリを `graphics/<キャラ>/<番号>/` に作り、
   `splash.webp`・`atlas.png`・`atlas.json`・`meta.json`・`contact.png` を置く。
   `meta.json` には現在の画風と画風バージョンを記録する。
   元の作業ディレクトリ（`spritekiln-v2*/`）はそのまま残す。コピーを置くこと。
6. `graphics/registry.json` にエントリを追加する（`status` は `候補`）。
7. ダッシュボードの素材タブに `addasset` で登録する
   （kind=画像、status=完成、fileName=`graphics/<キャラ>/<番号>/`、
   note に IoU・色数・状態・スプラッシュの GitHub raw URL、
   url にコンタクトシートの raw URL）。
   画風実験は素材登録しない（この設計書に記録する）。

## 採用の切り替え手順

1. `graphics/registry.json` の `current` を切り替え先の番号に変える。
2. 切り出し：`python3 tools/slice_atlas_hero.py`（既定は hero-001 のアトラス。
   別パターンの場合はアトラス PNG と JSON を引数で指定する）。
   アトラスは既に透明背景なのでマゼンタのキーアウトは不要。
   切り出しは内容の bounding box で切り抜き、2px パッド、最大辺160px、LANCZOS。
   向き対応は S=0, SW=1, W=2, NW=3, N=4, NE=5, E=6, SE=7。
   歩行は `walk_<dir>_0/2/4/6` → f0/f1/f2/f3、静止は `idle_<dir>_0` → idle。
3. 採用中のスプラッシュを `android/assets/splash/hero.png` に置き換える
   （webp→PNG、高さ1024px程度に縮小）。
4. `python3 tools/make_norm.py` で方向ごとの倍率を測り直す。
5. 品質ゲート：`python3 tools/check_hero_gate.py` で
   `samples/gate/hero_contact.png` と `samples/gate/hero_feet2x.png` を作り、
   **足シートを先に**フレーム単位で目視確認する。不良セルがあれば直してから進む。
   ゼロ不良を名乗るのは足シートを確認してから。
6. プレビュー：`python3 tools/preview_iso.py` で
   `samples/preview25d/`（lower／upper／debug）を再生成して目視確認する。
7. コミット（個別 add のみ、`git add -A` は禁止）→ push → CI 成功を確認 →
   nightly Release の APK・jar が更新されたことを確認する。
8. ダッシュボードに `addbuild` でビルドを記録する。

## 注意点

- **攻撃クリップはレンダリングされていない**。SpriteKiln のアトラスは
  歩行＋待機のみ（112フレーム）。攻撃はゲーム内の既存の処理
  （突進＋斬撃エフェクト）のまま使う。
- 図鑑・ステータス画面はまだ存在しない。スプラッシュは同梱のみで、
  画面の実装は別の作業。
- `samples/` は gitignore 済み。`spritekiln-v2*/` の作業ディレクトリは
  リポジトリにコミットしない（`graphics/` にコピーを置く）。
- SpriteKiln 0.4.0 の永続インストールは `~/workspace/tools/skvenv-chibi/`
  （`[fast]` 付き）と `~/skvenv2`。`/tmp` は VM 置換で消えるので使わないこと。
- 過去の経緯：2026-11-27 の最初のコミット（cd07e87）では、画風違いを
  hero-001〜005 として登録していたが、にゅーいちの修正で上記の扱いに直した。
  履歴の書き換えはしていない。cd07e87 はそのまま残っている。
